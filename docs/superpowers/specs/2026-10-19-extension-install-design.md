# Cordis 확장(zip) 설치 — A 층(설치 뼈대) 설계

작성: 2026-10-19 (브레인스토밍 합의 내용). 상태: 설계 합의 완료, 구현 전.

## 1. 배경과 범위

외부에서 zip 으로 받은 확장을 litecode 에 설치하는 기능. 지금 서비스는 전부 `electron/main.ts` 에 정적으로 묶여 있고, `features` 레지스트리가 `{ id, plugin(ctx), service? }[]` 를 받아 켜고 끈다. zip 설치는 이 목록을 런타임에 늘리는 일이다.

가장 큰 쟁점: **받은 zip 안의 코드가 메인 프로세스에서 실행된다.** 메인에는 provider 키·파일 시스템·키 프록시가 있다. 그래서 신뢰 모델을 먼저 정했다.

범위를 세 층으로 나눈다.

| 층 | 내용 | 난이도 |
|---|---|---|
| **A. 설치 뼈대** | zip 풀기 → manifest 검증 → 확장 폴더 보관 → 목록·켜기/끄기·삭제. 레지스트리가 런타임에 확장을 올리고 내림 | 중 |
| **B. 확장 코드 실행·권한** | 확장의 메인 쪽 코드를 어디서 어떻게 돌리나. 권한 선언, 동의 카드, 필요하면 별도 프로세스(utilityProcess)로 격리하고 `ctx` 일부만 RPC 로 노출 | 큼 |
| **C. 화면 조각** | 확장이 사이드바·오른쪽 패널 탭·입력 트리거·설정 카드에 UI 를 끼우는 방법. 슬롯과 샌드박스 iframe 중 선택 | 큼 |

- **이번 문서는 A 층만 다룬다.** A 는 B·C 가 꽂힐 자리를 정하고 먼저 단독으로 쓸 수 있게 만든다.
- **가이드 문서(확장 제작자용, `docs/` 마크다운)는 A 구현 뒤에 쓴다.** manifest 와 API 표면이 정해져야 쓸 수 있고, 미리 쓰면 어긋난다. 예제 확장을 하나 같이 만들어 단위 테스트로 설치해 보면 문서가 낡는 것을 막을 수 있다.

## 2. 확정된 결정

| 항목 | 결정 |
|---|---|
| 신뢰 모델 | 사용자가 직접 만든 것까지 받는다 (권한 선언·동의·격리가 설계에 들어간다) |
| 확장 범위 | 앱 기능까지 더한다 (AI 도구·스킬 + 화면 조각) |
| 적용 방식 | 설치·업데이트·삭제는 **앱 재시작 후** 적용 |
| 입구 | 설정 > 기능 화면 (기존 카드 모양, "확장 추가 (zip)" 버튼) |
| 개발 모드 | 없음. 모든 설치는 zip → 확인 단계를 지난다 (필요해지면 나중에 더함) |
| 구조 | 접근 1 — 별도 `ctx.extensions` 서비스. 닫힌 `FeatureId`·`FEATURES`·`features` 설정은 건드리지 않는다 |

접근 1 을 고른 이유: `FeatureId` 가 닫힌 목록이라 `enabled()`·`featureOn`·`isFeatureSwitches`·카드 글의 i18n 키 타입이 모두 이 목록에 묶여 있다. 확장 id 는 설치 때 정해지므로 목록에 들어갈 수 없다. 접근 2(`FeatureId` 를 `` `ext:${string}` `` 까지 넓힘)는 기존 기능 코드를 건드려 위험하고, 접근 3(확장 호스트를 기능 한 줄로)은 "확장도 카드 하나씩 + 토글" 모양이 안 나온다. 단점은 올리고 내리는 큐·상태 표시(mounting/failed)를 `features` 와 일부 중복해 만드는 것.

## 3. 설계 1 — zip 구조와 manifest

```
my-extension.zip
└─ extension.json     ← 필수, 최상위 (또는 폴더 하나로 감싼 경우 그 안)
   index.js           ← 진입 파일 (B 층에서 내용 규칙 확정)
   …                  ← 자유 (스킬 폴더, 자산 등)
```

### `extension.json` 필드 (A 층에서 확정)

| 필드 | 규칙 |
|---|---|
| `id` | 필수. 소문자·숫자·하이픈 3~40자. 폴더 이름과 설정 키로 쓰이므로 엄격. 기존 기능 id(`FEATURES`)와 같으면 거절 |
| `name` | 필수. 카드 제목 (문자열 하나, 다국어는 필요해질 때 더함) |
| `description` | 필수. 카드 설명 한 줄 |
| `version` | 필수. semver. 같은 id 재설치 때 업그레이드/동일/다운그레이드 판정에 씀 |
| `litecode` | 선택. 필요한 최소 앱 버전. 앱이 더 낮으면 설치 거절 |
| `entry` | 필수. 진입 파일 상대 경로. 패널 확장(#511)은 `.html`·`.htm`, 언어 팩(#525)은 번들 `.json` |
| `permissions` | 선택. 문자열 배열. A 층은 모양만 검증, 의미는 B 층 |
| `details` | 선택 (#519). 카드 상세의 여러 줄 설명(2000자, 글로만). 켜는 법·쓰는 법을 여기 적는다 |
| `type` | 선택 (#525). `panel`(생략 시) 또는 `locale`(언어 팩, 코드 실행 없음). 그 밖은 `type-invalid` |
| `locale` | `type: "locale"` 일 때 필수, 아니면 거절(`locale-unexpected`). `{ language, label }` — language 는 BCP47 모양(`zh-CN`), 내장 ko·en 과 겹치면 `locale-reserved`. label 40자 |

언어 팩 번들(#525): 앱 사전에 있는 키의 문자열만 쓰이고, 빠진 키는 영어로 보인다(1MB·키 5000개·값 2000자 상한). 설치만으로 적용되지 않고 설정 > 일반 > 언어에서 고를 때 적용되며, 고른 팩을 끄거나 지우면 en 으로 돌아간다.

모르는 필드는 무시하지 않고 **거절**한다 (`permisions` 같은 오타가 조용히 넘어가면 권한 선언이 빠진 채 설치되기 때문).

### zip 안전 검사 (풀기 전, 목록만 보고)
- 경로가 `..` 이거나 절대 경로이거나 심볼릭 링크인 항목이 있으면 전체 거절 (zip-slip).
- 파일 수와 풀었을 때의 총 크기에 상한 (zip bomb 방지). 값은 구현 계획에서 정함.
- 폐쇄망 규칙: zip 해제 라이브러리도 앱에 동봉한 것만 쓴다.

### 가정
- `extension.json` 은 최상위나 단일 폴더 안 한 곳에서만 찾는다.
- 설치 때 의존성 설치(`npm install`)는 하지 않는다. 필요한 모듈은 확장이 zip 에 직접 넣는다.

## 4. 설계 2 — 설치 흐름과 검증

메인의 `ctx.extensions` 서비스가 전부 맡는다. 파일 선택 대화상자와 경로는 기존 서비스처럼 host 설정으로 받아 Electron 없이 단위 테스트가 된다.

### 설치는 2단계 (확인 카드가 사이에 들어감)
1. **검사 (`pick`)**: host 가 대화상자로 zip 을 고르면, 서비스가 zip 을 **앱 임시 폴더(`staging/`)로 복사**해 두고(`token` 발급) 목록만 읽어 검사한다. 풀지 않는다. 결과: manifest 미리보기, 파일 수·크기, 같은 id 가 이미 있으면 그 버전, 거절 사유 목록. 거절 사유가 하나라도 있으면 거절 화면.
2. **설치 (`install(token)`)**: 확인 카드에서 "설치"를 누르면 임시 복사본만 쓴다. 원본 zip 을 다시 읽지 않으므로 확인~설치 사이에 파일이 바뀌어도 영향이 없다.

### 풀기·교체는 "보류"로 쌓고 다음 부팅 때 한다
- `install` 은 `pending/` 에 풀어 두고 보류 작업(`install`/`remove`)을 기록하기만 한다. 실제 교체는 **다음 부팅 때, 확장이 로드되기 전에** 한다.
- 재시작 방식에 맞는 선택: 실행 중인 확장 파일을 건드리지 않아 Windows 파일 잠금이나 지연 로드 중 파일이 사라지는 문제가 없다. 업그레이드 롤백도 단순해진다 (새 버전이 다 풀렸는지 확인한 뒤에야 옛 폴더와 바꾼다).
- 업그레이드·같은 버전 재설치·다운그레이드는 모두 허용하고 확인 카드의 문구만 달리한다.
- 삭제도 같은 방식: 카드에는 "삭제 예정"으로 보이고, 다음 부팅 때 폴더와 켜짐 값을 지운다.

### 검증은 두 번
zip 목록 단계에서 경로·상한을 검사하고, 풀린 결과에서 한 번 더 본다 (심볼릭 링크, 실제 크기, `extension.json`, 진입 파일 존재).

## 5. 설계 3 — 저장 위치, 켜짐 값, 부팅 로드

```
<userData>/extensions/
  installed/<id>/      ← 풀린 확장 (extension.json + 파일들)
  pending/             ← 보류 작업 목록 + 풀어 둔 새 버전
  staging/             ← pick 때 복사해 둔 zip (설치·취소 때 지움)
```

- **켜짐 값**: `settings.extensions` 에 `{ [id]: boolean }`. 기존 `features` 처럼 기본값(켜짐)과 다른 값만 남긴다. 설치 확인이 곧 동의라 기본은 켜짐. `FEATURES` 상수와 `features` 설정은 건드리지 않는다.
- **부팅 순서**: (1) 보류 작업 적용 → (2) `installed/` 를 읽어 manifest 재검증 → (3) 켜진 확장마다 올림.
- **함정 4번(서비스 생성자가 던지면 영영 안 뜬다) 대응**: 확장 하나가 깨져도 생성자는 던지지 않는다. 그 확장만 "올리지 못함 + 사유" 상태로 목록에 남고(삭제 가능), 앱 부팅은 막지 않는다.
- **`mount` 주입 자리**: `features` 의 `definitions` 와 같은 패턴으로, 서비스가 `mount(extension)` 함수를 설정(host)으로 받는다. A 층 단독으로는 `mount` 가 아무것도 실행하지 않고 상태만 "켜짐"으로 둔다. 실제 코드 실행과 권한은 B 층에서 이 자리에 주입한다.
- **켜기/끄기 즉시 적용**: `extensions:set-enabled` 가 설정 값을 바꾸고, 서비스가 자기 올리기/내리기 큐로 해당 확장만 올리거나 내린다. (설치·업데이트·삭제만 재시작.)
- **IPC (브리지 패턴, effect 로 건다)**: `extensions:list`, `extensions:pick`, `extensions:install`, `extensions:remove`, `extensions:set-enabled`, 이벤트 `extensions:changed`. 화면은 확장 카드 목록을 `features` 목록과 합쳐 그린다.
- **단위 테스트** (실물 테스트 없음, 테스트 코드가 zip 을 직접 만들어 씀): zip-slip·심볼릭 링크·크기 상한 거절, 알 수 없는 필드 거절, 보류 설치의 부팅 적용, 업그레이드 도중 실패 시 롤백, 삭제, 깨진 폴더가 있어도 나머지가 뜨는지, 설정 값 검증.

## 6. 화면 시안

https://claude.ai/artifact/Cg7SfNA9ZuKcMKmWpWZd3P (비공개 링크, 3보드)

1. **설정 > 기능 화면**: 기존 카드 모양. 검색창 옆 "확장 추가 (zip)" 버튼, "설치한 확장" 구분선 아래 확장 카드(보라색 "확장" 뱃지·버전). 상태 세 가지를 한 장에 — 정상, 올리지 못함(빨간 사유 줄), 방금 설치해 재시작 대기(점선 카드·토글 비활성). 상단에 "앱을 다시 시작하면 올라옵니다" 배너와 "지금 다시 시작" 버튼. 카드 `⋯` 메뉴는 정보 보기·삭제(재시작 필요).
2. **설치 확인**: manifest 미리보기 — 이름·id·파일 크기와 개수·필요한 앱 버전·요청 권한("없음", B 층 전까지)·같은 id 가 있으면 "v1.1.0 → v1.2.0 업그레이드", 사용자 제작 코드 경고 문구.
3. **설치 거절**: 안전 검사에 걸렸을 때. 거절 사유를 줄로 나열(폴더 밖 경로, 알 수 없는 필드 등)하고 아무것도 설치하지 않았다고 알림.

## 7. 구현 가능성 점검

A 층은 개발할 수 있다.

- 기존 패턴 있음: `electron/*Host.ts`(대화상자·경로 host 주입), `jsonFile.ts`(`readJsonFileSync`), `features.ts` 의 올리기/내리기 큐·상태 표시. 새 서비스 절차는 `docs/cordis-services.md` 9절.
- **zip 라이브러리는 `dependencies` 에 직접 추가해야 한다.** `yauzl`·`extract-zip` 이 `node_modules` 에 있지만 `electron`(devDependency)이 끌고 온 것이라 설치본에 실리지 않는다. 순수 JS 라 네이티브 빌드·폐쇄망 문제는 없고, 목록을 풀기 전에 읽는 "검사" 단계와도 맞는다.

| 부분 | 위험 | 이유 |
|---|---|---|
| zip 검사·manifest 검증 | 낮음 | 순수 함수, 테스트 쉬움 |
| 보류 설치·부팅 적용·롤백 | 중간 | 파일 시스템 작업, 중간 실패 시나리오 테스트가 핵심 |
| 서비스·설정·IPC | 낮음 | 기존 패턴 반복 |
| 화면(카드·확인·거절) | 낮음~중간 | 기능 목록과 확장 목록을 합쳐 그리는 부분만 새로움 |
| Windows | 미검증 | 이 머신에서 실행 불가. 부팅 때 교체하는 방식이라 파일 잠금 위험은 줄였지만 확인은 못 함 |

### 한계 두 가지
1. A 만 끝나면 사용자에게 보이는 기능은 없다. 설치·목록·켜기/끄기만 되고 확장 코드는 아직 실행되지 않는다. 진짜 난관은 B 층이고 이 설계에서 가장 불확실하다. A 의 `mount` 주입 자리가 B 방식에 따라 달라질 수 있으므로, A 를 하는 동안 B 의 큰 방향을 미리 정해두는 편이 안전하다.
2. 실물 테스트를 쓰지 않는 규칙이라, 실제 Electron 창에서 대화상자를 거쳐 설치하는 경로는 단위 테스트로 못 덮는다. 직접 눌러서 확인해야 한다.

## 8. 구현 순서 (PR 4개 정도)

1. zip 검사와 manifest 검증, `yauzl` 추가 (순수 함수와 테스트)
2. 보류 설치·삭제·부팅 적용과 롤백 (파일 작업과 테스트)
3. `ctx.extensions` 서비스, `settings.extensions`, IPC·preload 브리지
4. 설정 > 기능 화면 (카드, 확인, 거절)

가이드 문서는 3 이후에 쓴다.
